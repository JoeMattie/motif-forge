# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Commands

- `npm run dev` — Vite dev server (http://localhost:5173)
- `npm run build` — TypeScript strict check (`tsc -b`) + production build; must pass with zero errors
- `npm test` — Vitest unit tests (`tests/*.test.ts`) covering the pure core modules (`src/core/`, `src/api/parse.ts`); `npm run test:watch` for watch mode
- `npm run test:e2e` — Playwright end-to-end tests (`e2e/*.spec.ts`); auto-starts the dev server, and `e2e/helpers.ts` intercepts the Anthropic proxy route with `page.route` so no API key or network is needed. One-time setup: `npx playwright install chromium`. Note: `MOTIFS_ADDED` auto-selects the first added motif, so the first seed card is already selected on load.

Vitest and Playwright are dev-only dependencies (test-tooling amendment to the brief's minimal-deps rule); runtime deps are unchanged.

The full spec is [motif-forge-project-brief.md](motif-forge-project-brief.md) — the source of truth for scope, data model, validation rules, and success criteria.

## Architecture

Vite + React 19 + TypeScript strict. Runtime deps: `react`/`react-dom`, `@mantine/core`/`@mantine/hooks` (UI components), `@phosphor-icons/react` (icons — an amendment to the design handoff's text-glyph suggestion), `tone` (synth playback), `smplr` (sampled instruments). The MIDI writer, WAV encoder, and IndexedDB wrapper remain hand-rolled by design; do not add libraries for those.

**UI design: "Workbench"** (spec: the design handoff in `Motif Forge UI Design.zip`) — a Teenage-Engineering-style hardware panel: matte plastic modules, chunky 3D-shadowed keys, rotary knobs, toggle switches, with all piano rolls on inset dark LCD screens. Two themes, **Day** (light, default) and **Nite** (dark), plus follow-system, toggled in the header: every color is a semantic CSS custom property on `:root[data-theme='day'|'nite']` in `src/styles.css` (accents + LCD tokens are shared; only panel tokens swap; plain `:root` carries the Day fallback pre-hydration). `main.tsx` resolves the preference (`uiPrefs.ts`, localStorage) to `data-theme` and Mantine's `forceColorScheme` in lockstep. Fonts: Space Grotesk (panel) + IBM Plex Mono (LCDs), loaded from Google Fonts in `index.html`.

Buttons are Mantine `Button`s skinned as hardware keys: the theme stamps `wb-btn` on every Button root and `styles.css` styles the default variant (uppercase micro text, 3D key shadow; modifier classes `accent`/`green`/`dark`/`dashed`/`danger-text`; `data-latched` renders a flat dark fill in Day, an inset well + LED dot in Nite; `data-danger` for armed destructive keys). **Button labels that mix text with other nodes must be wrapped in a single `<span>`** — the label slot is a flex container that collapses whitespace between bare text nodes; standalone icons go in `leftSection`/`rightSection`. Hotkey letters inside labels are Mantine `Mark className="hk"` (accent underline — adds no width, so mid-word letters don't shift or split); standalone key tokens in legends are Mantine `Kbd` (`wb-kbd`). Segmented switches (header Grid/Focus + theme icons, generation bars) are Mantine `SegmentedControl` (`wb-seg*`); quiet ✕ icon buttons are `ActionIcon` (`wb-action`). Still hand-rolled: `src/components/hw/` (`Knob` — drag/wheel/arrow rotary, `HardToggle`, `PlayRound`, `RateSquares`) and `LcdRoll` (the LCD piano roll — melodic parts map pitch→y, drum-part notes draw as short ticks on a bottom lane, velocity→opacity, `dimParts` fades context parts). Mantine also provides `Select`/`TextInput`/`Textarea`/`Tooltip`/`Menu`/`Slider`/`NumberInput`/`Drawer`/`Badge`/`Group`/`Stack`, restyled in `src/theme.ts` against the surface tokens. Hover descriptions are Mantine `Tooltip`s — don't use `title` attributes for them. The `:root` font-size of 13px deliberately shrinks Mantine's rem-based component dimensions; text sizes are pinned in px in the theme, so keep both in sync. Mantine's PostCSS preset is configured in `postcss.config.cjs`.

**Families.** A family = a root motif + all lineage descendants (`src/core/families.ts` — derived from `source`, not stored). The triage grid shows exactly ONE card per family: its **face** (the `promoted` member, else the root); variants live in a fold-out tray (`FamilyTray`, F key or the FAMILY chip) inserted full-width under the card's row, so pool counts never inflate. Filters and triage progress count families; discarding a grid card discards the ROOT (variants keep their own flags); PROMOTE/KEEP moves the `promoted` flag (one per family — `MOTIF_PROMOTED` carries all `familyIds` so the write-through persistence saves every member). Concept tags apply family-wide (`FAMILY_ASSIGNED_CONCEPT`).

**Screens.** `view` + `triageMode` drive the shell (`App.tsx`): Triage grid (`TriageGrid`) or Focus deck (`FocusTriage` — large LCD, prev/play/next cluster, rate keypad with auto-advance, queue strip, session-pace telemetry from `store/sessionPace.ts`); Library (`LibraryView` — ★-gate keys, concept filter/chips, EXPORT ALL .MID of promoted takes); Concepts (`ConceptView` — leitmotif desk: per-root trays, derived-variant cards with `trackId` chips, play-all-in-sequence, TRANSFORM FOR NEW TRACK opens the bay). The Mutation Bay (`MutationBay`) slides up in a bottom Mantine `Drawer` over whatever view is active (`mutationTargetId` via `SET_MUTATION_TARGET`; `closeOnEscape`/`trapFocus` off — the bay owns its keyboard); the triage keydown listener is disabled while it's open.

- `src/core/` — pure, framework-free domain logic: `theory.ts` (mode intervals, pitch↔scale-degree math; chromatic pitches decompose to nearest-degree-below + offset so mode swap is total), `transforms.ts` (deterministic transforms; each returns a child motif with lineage in `source`), `validate.ts` (LLM JSON → Motif with drop/warn counts; **polyphony allowed, ≤8 simultaneous voices**; in-scale violations warn, never drop; all float comparisons use `EPS = 1e-6`), `midi.ts` (SMF format-0, 480 TPQN; note-off sorts before note-on at equal ticks), `wav.ts`.
- `src/audio/` — `instruments.ts` is the adapter over two backends behind one `Instrument` interface: `'synth'` = Tone.js PolySynth (no network; built per playback with the part's optional `SynthPreset`, disposed on stop) and smplr sampled sounds (piano/e-piano/marimba/strings; CDN-fetched on first use, `CacheStorage`-cached, cached per context by the engine; smplr's `stop()` does NOT cancel notes queued in its internal scheduler — the adapter collects each `start()`'s returned stop function and fires them all in `stopAll`; each cached smplr instrument also sits behind its own engine-owned gain that stop hard-mutes in ~15ms so release tails decay silently, un-muted again just before the next playback that uses it — both are needed for stop to be instant). Playback routes each note to its part's instrument (`scheduleMotif(instruments[], …)`); partless motifs use the transport-bar sound picker, and the transport "force" toggle (`transport.forceSound`) overrides parts to audition everything through the picked sound. Drum parts play a hand-built Tone kit (MembraneSynth/NoiseSynth/MetalSynth mapped from GM pitches) — transient per playback like synth parts. Master chain, metronome, and drone stay hand-rolled raw WebAudio in `voice.ts` against `BaseAudioContext`, shared by live playback and WAV export. Offline render (`renderOffline.ts`) uses one `Tone.OfflineContext` for everything: Tone parts bind to it, smplr parts bind to its `rawContext`, and `.render()` drives Tone's clock while the raw graph renders alongside — mixed-instrument motifs render in a single pass. `engine.ts` is a singleton holding all playback state **outside React**; components subscribe via `useSyncExternalStore` and the playhead is one rAF loop mutating an SVG ref — the grid must never re-render per frame. Motifs are ≤8 bars, so everything is scheduled up front at absolute context times (no lookahead loop); `play()` awaits all part instruments' `ready` promises first (snapshot exposes `loading`), guarded by a token against stale async scheduling.
- `src/api/` — Anthropic API client (`claude-sonnet-4-6`) calling through the Vite dev-server proxy at `/api/anthropic/*` (see `vite.config.ts`), which injects `x-api-key` (from `ANTHROPIC_API_KEY` in `.env.local`) and `anthropic-version` server-side — the browser must never call `api.anthropic.com` directly (CORS + key exposure). Prompt builders (enumerate allowed pitch classes concretely; texture rule from `GenerationBrief.texture`: `'lead'` = melodic line + light harmony ≤4 voices, `'poly'` = free polyphony ≤6 voices; `includeRhythm` demands a drums part; mutation supports `lockRhythm` — children keep exact note timings, only pitches change; "surprise" prompts give the model free rein over key/mode/tempo/bars — per-motif `tempo` is parsed and clamped in validation), fence-stripping JSON extraction, and batch orchestration. All LLM calls go through `queue.ts` (concurrency 2); each queued batch dispatches `BATCH_QUEUED`/`BATCH_FINISHED` and renders as a pulsing placeholder card in the triage grid. Generation is chunked to ≤5 motifs per call (polyphonic multi-part JSON is bulky); LLM mutations default to 5 children. Prompts demand minified JSON and `max_tokens` is 16000 — a `max_tokens` stop reason means truncated JSON — retry smaller, never parse it.
- `src/generation/symbolic/` — Tier 1 of the offline-generation plan ([motif-forge-offline-generation-spec.md](motif-forge-offline-generation-spec.md)): fully offline, deterministic batch generation, selectable via the generation panel's ENGINE switch (INSTANT vs CLAUDE; Claude stays the default until the spec's Phase 6 flips it). Every generator draws from a seedable mulberry32 PRNG (`prng.ts` — never `Math.random` inside generators; the seed is stored in `source`, so any motif is reproducible). `walk.ts` is a constrained random walk: pitch moves in scale-degree space only (always in-key), pulled toward a contour template (arch/ascend/descend/zigzag/flat), with leap-recovery (a leap > a third resolves by a step in the opposite direction) and per-beat rhythm-archetype cells (straight/dotted/syncopated/sparse) on a 16th grid. `genetic.ts` evolves the user's kept motifs (non-discarded, rating ≥ `KEEPER_MIN_RATING` = 3): bar-boundary crossover (the tail parent re-spelled degree-for-degree into the head parent's key/mode) plus small in-scale mutations; `index.ts` mixes crossovers/mutants/fresh immigrants per `GA_RATIOS` with a fresh-diversity floor and returns a `ValidationResult`, so it plugs into the same queue/dispatch path as LLM batches. GA children are partless melodic lines that start their OWN family — fresh triage cards, with ancestry kept in `source.parentIds`, which `parentIdOf` deliberately ignores. New `MotifSource` kinds: `symbolic` (fresh walk) and `ga` (1 parentId = mutant, 2 = crossover).
- `src/store/` — Context + reducer. Persistence is a write-through wrapper around dispatch in `AppContext.tsx` targeting the `PersistenceAdapter` interface (`idbAdapter` in prod, `memoryAdapter` for tests). Lineage is the `source` field on each motif (`parentId` denormalized only in the IDB records). Discard is a soft flag, not a delete.
- `src/components/` — triage grid is the primary screen. Keyboard triage is a single window keydown listener (`hooks/useKeyboardTriage.ts`) gated on selection state, not DOM focus, with a typing-target guard; up/down movement goes through `core/gridNav.ts` (`verticalTarget` — strictly vertical, no sideways clamp on partial rows); `f` folds the family tray, `m` opens the mutation bay.
- **Mutation Bay** (`MutationBay` + `components/bay/`) — a per-part variation workspace scoped to ONE source motif, persisted as `PartVariation` records (`src/core/workbench.ts` is the pure model: per-part trees keyed on `sourceMotifId`, ≤1 `selected` node per part, composite assembly). One `PartRow` per part with a sticky origin cell; MUTATE fires an instant LLM batch on that part only (`partMutationBrief`, all other parts locked via `lockedParts` — `lockedPartsRoundTrip` still drops violators); ADVANCED adds part-scoped deterministic transforms (no Aug/Dim — they'd desync one part's bar count) and a custom brief. Results nest rightward as a tree (CSS elbow connectors, no measured SVG). Enter selects a take per part; Space loops the composite mix (`compositeMotif`, id `` `${source.id}::mix` `` — the transport strips `::` suffixes when resolving names); selection changes while looping swap on the next bar boundary via `loop`/`fromBeat`. A transport strip at the top shows the mix with per-part take Badges. PROMOTE MIX adds the composite to the family (`source: { kind: 'bay-mix' }`); REBASE hides off-path takes, SHOW HIDDEN ghosts them back, PRUNE hard-deletes (PartVariations are the one entity that is hard-deleted; motifs stay soft-discard). Trees persist in the `partVariations` IDB store (DB v2 — `onupgradeneeded` guards every `createObjectStore`).

## What this is

Motif Forge: a local-first, single-page web app for generating, auditioning, mutating, and exporting short melodic motifs (2–8 bars, polyphonic) as MIDI/WAV. Motifs are generated in batches via the Anthropic API, triaged by ear with a keyboard-first UX, mutated (deterministically client-side or via LLM), tagged to song concepts (leitmotif management), and exported for use as Suno seed audio.

## Hard constraints (from the brief, as amended)

- **Minimal dependencies.** Everything runs in the browser: melody generation, Web Audio playback, mutation, MIDI/WAV export. No DAW, no Python, no native binaries. Permitted libraries: `tone` and `smplr` for playback instruments, `@mantine/core`/`@mantine/hooks` for UI components, and `@phosphor-icons/react` for icons (all later amendments to the brief's zero-dep rule), plus the Anthropic API. The MIDI file writer (SMF format 0) and WAV encoder stay hand-rolled — do not add libraries for those. smplr fetches instrument samples from a CDN on first use; everything else works fully offline.
- **Anthropic API**: `POST https://api.anthropic.com/v1/messages` with model `claude-sonnet-4-6`; no API key needed in this environment. Response `data.content` is an array of blocks — concatenate `.text` fields, strip markdown fences, `JSON.parse` in try/catch. Batch size is ~5 motifs per call (amended down from the brief's 10–20 once motifs went polyphonic — the JSON no longer fits otherwise); the UI accumulates batches toward ~100 candidates.
- **If built as a Claude artifact**: no `<form>` tags (use onClick handlers) and no localStorage/sessionStorage (use `window.storage`); standalone builds use IndexedDB. Persistence must go through a thin swappable interface — decide the target once at project start.

## Core data model

A motif is a note list `{ pitch (MIDI number), startBeat, durationBeats, velocity, part? }[]` plus `parts` (up to 6 — `MAX_PARTS` in `validate.ts`; prompts ask for 1–4 by default, 4–6 with the generation panel's EXTRA toggle (`GenerationBrief.extraInstruments`): `{ name, instrument, preset? }` — the LLM picks instruments per part, may sound-design `synth` parts with an oscillator+ADSR preset (clamped in validation), and may include a `drums` part using GM drum pitches: kick 36, snare 38, hats 42/46 etc. — drum-part notes are exempt from the scale check, allowed down to pitch 35, play through a hand-built Tone drum kit, and export to MIDI channel 9) and metadata (key, mode, tempo, time signature, tags, generation lineage). Notes may overlap (polyphonic; validation caps at 8 simultaneous voices — this amends the brief's monophonic-MVP rule). `parts: []` means partless — played on the transport-bar sound; records from before this migration are normalized in `idbAdapter.loadAll`. MIDI export maps parts to channels with GM program changes. Every mutation records its parent motif and the transformation applied. Remaining validation rules per the brief: pitches 36–96, notes within bar count, ≥3 notes, in-scale unless chromaticism requested (warn rather than drop for scale violations only).

## Build order

Follow the brief's incremental sequence — each step must leave the app working and demoable:

1. Data model + hand-rolled synth playback + piano-roll rendering (against 3 hardcoded motifs)
2. MIDI export + WAV export (verify files open/play correctly)
3. Claude API generation with JSON validation
4. Triage UX (arrow keys, space to play, `1`–`5` to rate, `x` to discard)
5. Deterministic transforms (inversion, retrograde, transposition, augmentation/diminution, mode swap, octave displacement)
6. LLM mutations + lineage display
7. Library persistence + concept/leitmotif view

## Design intent

Hardware workbench aesthetic (light "Day" panel by default, "Nite" after hours) — physical, immediate, no springy motion (transitions ~80–180ms). The triage grid is the primary screen — optimize for speed and low visual noise. LCD piano rolls are the visual anchor; playback state must be unmissable (orange outline + glow, orange stop button, sweeping orange playhead). The default synth timbre is deliberately plain so the user judges melodic bones; sampled instruments are opt-in via the transport-strip sound picker.

## Out of scope for MVP

Drum patterns, audio input/transcription, Suno API integration (manual file upload is the handoff), multi-user, auth, mobile polish, zip batch export.
