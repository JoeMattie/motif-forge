# Phase 0 findings — SkyTNT midi-model for the neural tier

Verified 2026-07-02 against `SkyTNT/midi-model` @ main (app v1.3.5) and the
HuggingFace ONNX exports, per the offline-generation spec
([motif-forge-offline-generation-spec.md](../motif-forge-offline-generation-spec.md), Phase 0).
All numbers below were measured locally, not taken from docs.

## Decision: `skytnt/midi-model-tv2o-medium`

The spec's "smaller alternative" hypothesis is **false**: the original v1.2
repo's ONNX pair (782 + 109 MB) is byte-for-byte the same *medium* network —
only the tokenizer differs (V1, vocab 3239, no key/time-signature events).
Since v1.2 buys no size and loses the key-signature and time-signature
conditioning we specifically want for in-key 4/4 motifs, **tv2o-medium wins
outright**. No quality comparison was needed.

## Model facts (verified)

Two Llama-style decoders sharing one vocab (`config.json` in the HF repo):

| | `model_base` (event-level) | `model_token` (sub-token) |
|---|---|---|
| layers | 12 | 3 |
| heads | 16 (head_size 64) | 4 (head_size 256) |
| hidden / intermediate | 1024 / 4096 | 1024 / 1024 |
| max position | 4096 | 4096 |
| fp32 ONNX size | 821,713,887 B (783 MB) | 116,661,381 B (111 MB) |
| int8 size (this repo's tooling) | 207,138,439 B (198 MB) | 29,640,678 B (28 MB) |

## ONNX I/O (verified by loading the published exports, opset 14)

- `model_base`: `x` int64 `[batch, mid_seq, token_seq]` → `hidden` f32
  `[batch, mid_seq, 1024]`, plus 12 KV pairs
  `past_key_values.{i}.key/value` f32 `[batch, 16, past_seq, 64]` →
  `present.{i}.key/value` `[batch, 16, present_seq, 64]`.
- `model_token`: `hidden` f32 `[batch, states, 1024]` + `x` int64
  `[batch, token_seq]` → `y` f32 `[batch, token_seq1, 3406]`, plus 3 KV pairs
  shaped `[batch, 4, past_seq, 256]`.
- **Batch dim is dynamic** in both exports — batched candidate generation
  needs no re-export (spec risk #2 resolved).
- The reference loop feeds **zero-length tensors** routinely: empty KV caches
  `[b, h, 0, hs]` on the first step, `x` of shape `[b, 0]` on the token
  model's first sub-token, `hidden` of shape `[b, 0, 1024]` on subsequent
  ones. onnxruntime (CPU) accepts all of these; **verify onnxruntime-web's
  WebGPU EP does too** — this is the main Phase 4 unknown. Fallback: pad and
  mask, or skip cache on step one.

## Tokenizer facts — `MIDITokenizerV2`, `optimise_midi=True` ("tv2o")

- `vocab_size` **3406**, `max_token_seq` **8** (event id + up to 7 params).
- Special ids: pad **0**, bos **1**, eos **2**. Event ids: note 3,
  patch_change 4, control_change 5, set_tempo 6, time_signature 7,
  key_signature 8.
- Parameter id ranges (first, last): time1 (9, 136), time2 (137, 152),
  duration (153, 2200), track (2201, 2328), channel (2329, 2344),
  pitch (2345, 2472), velocity (2473, 2600), patch (2601, 2728),
  controller (2729, 2856), value (2857, 2984), bpm (2985, 3368),
  nn (3369, 3384), dd (3385, 3388), sf (3389, 3403), mi (3404, 3405).
- Event schemas (field order matters; a token row is
  `[event_id, params..., pad...]` to length 8):
  - `note`: time1, time2, track, channel, pitch, velocity, duration
  - `patch_change`: time1, time2, track, channel, patch
  - `control_change`: time1, time2, track, channel, controller, value
  - `set_tempo`: time1, time2, track, bpm
  - `time_signature`: time1, time2, track, nn, dd — stored as nn−1, dd−1
    where dd indexes {1:/2, 2:/4, 3:/8}
  - `key_signature`: time1, time2, track, sf, mi — stored sf+7 (0–14), mi 0/1
- **Time encoding**: the grid is 16 steps per beat. `time1` is the *delta in
  whole beats* from the previous event (0–127); `time2` is the 16th-note
  position *within* the beat (0–15). `duration` is in 16ths (1–2047).
  Detokenize renders at 480 ticks/beat.
- Overlap rule: tokenize truncates an earlier note of the same
  (channel, pitch) at the next one's onset and drops it if that leaves zero
  length; detokenize does the same backwards pass.
- Setup optimisation: tokenize zeroes the time of leading meta events and
  dedupes them; events sort by (time1, time2, track, type-order) with
  type-order time_signature < key_signature < set_tempo < patch_change <
  control_change < note.

## Golden fixture

`tests/fixtures/neural-golden.json` (generated by
`tools/quantize/make_golden.py`): a hand-built 4-bar polyphonic score
(2 melodic channels + drums on channel 9, tempo/time-sig/key-sig/CC) →
27 token rows → detokenized score, all straight from the Python reference.
The Phase 3 TS tokenizer must reproduce `encode.tokens` byte-for-byte from
`encode.inputScore`, and `decode.outputScore` from those tokens. The fixture
also embeds the full vocab layout for asserting the TS port's tables.

`tools/quantize/samples/reference-fp32-seed42.json` records a full seeded
generation (prompt construction + all sampled tokens + I/O metadata) for
engine-level sanity checks.

## Sampling loop (ported reference: `app_onnx.py` `generate()`)

- Event loop: run `model_base` over new event rows with the KV cache; take
  the last `hidden`. Sub-token loop: `model_token` decodes up to 7 params,
  with its own per-event KV cache, masked so only legal ids can be sampled
  (event ids + eos at position 0; the event's parameter range at position
  i>0; pad once params are exhausted).
- Sampling = softmax(logits/temp) · mask, then top-p (cumsum over descending
  probs), then top-k, renormalize, categorical draw. Defaults: temp 1.0,
  top_p 0.94, top_k 20. No repetition penalty anywhere — do not add one.
- Melodic constraint hooks (all verified in the reference): disable channels
  (mask channel param ids), disable patch_change / control_change (mask event
  ids at position 0). Priming = prompt rows: bos, time_signature,
  key_signature, set_tempo, patch_change per instrument.
- KV cache trimmed to the last 4095 positions when past_len > 4095 (we never
  get near this for motifs).

## Throughput (macOS arm64, onnxruntime 1.27 CPU EP, batch 1)

| precision | events/s | 64-event phrase |
|---|---|---|
| fp32 | ~21 | ~3.1 s |
| int8 | ~40–50 | ~1.4 s |

An event ≈ one note. A 4-bar motif is ~16–40 note events, so even the CPU
already beats the spec's 5 s first-motif target; WebGPU has generous headroom
(and int8 op coverage on the WebGPU EP — spec risk #4 — should be validated
in Phase 4, with fp16 as the fallback).

## int8 validation (Phase 1 acceptance)

`quantize_dynamic` (QInt8, MatMulConstBOnly) on both models. Seeded runs at
42/7/123 produce structurally coherent output: 64/64 events decode to notes,
in-key ratios 0.97–1.0 vs the prompted key signature, sane registers and
durations, tracks/patches respected. Sampling diverges from fp32 after the
first logit difference, so outputs differ per seed — that is expected, not
degradation. Six comparison files (fp32 vs int8 at three seeds) are in
`tools/quantize/samples/` for the **manual listening pass, which is the final
accept gate** before the int8 artifacts ship.

## Local testing (before hosting is decided)

Serve the int8 artifacts from the app's own dev server:

```sh
mkdir -p public/models
cp tools/quantize/dist/*.onnx public/models/
```

`public/models/` is gitignored; the client fetches from `/models/` by
default (`VITE_MODEL_BASE_URL` overrides). Then: dev server → generation
panel → ENGINE: NEURAL → ENABLE. Note `npm run build` copies `public/` into
`dist/`, so remove the local copies before judging build size.

## Hosting

Artifacts are content-hashed (`model_base.q8.<sha8>.onnx`,
`tools/quantize/dist/manifest.json` records names/sizes/hashes; `dist/` is
gitignored). Recommendation: upload to a HF model repo (CORS-friendly
`resolve/main` URLs, free bandwidth) and pin the manifest into the app at
Phase 5; same-static-host works identically if we prefer bundling.
